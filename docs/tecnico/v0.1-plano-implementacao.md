# Projeto Encontros - Plano Tecnico de Implementacao - v0.1

## Objetivo do documento

Este documento define o plano tecnico para implementar a versao `0.1 - Fundacao` do Projeto Encontros.

Ele descreve a ordem de implementacao, estrutura da solucao, camadas, projetos, dependencias, banco de dados, contratos de API, testes e criterios tecnicos de validacao.

Este documento nao executa a implementacao. Ele serve como roteiro tecnico antes do inicio do codigo.

## Escopo tecnico da v0.1

A versao `0.1` deve implementar apenas a fundacao:

- cadastro de usuario
- login
- renovacao de sessao
- logout
- criacao de grupo
- listagem dos grupos do usuario
- visualizacao basica de grupo
- convite para grupo
- listagem de convites pendentes
- aceite ou recusa de convite
- listagem de membros
- remocao basica de membro

Nao devem ser implementados encontros, memorias, arquivos, notificacoes push, listas colaborativas, linha do tempo, setlists ou funcionalidades sociais.

A primeira implementacao da `v0.1` sera **backend-only**, conforme registrado em `decisoes-tecnicas.md`.

O cliente mobile sera adiado ate que o backend da fundacao esteja funcional, testado e documentado.

## Stack da implementacao

### Backend

- C#
- .NET 10 LTS
- ASP.NET Core Web API
- Entity Framework Core
- PostgreSQL
- JWT
- Refresh Token
- FluentValidation
- Swagger
- xUnit

### Mobile

- Adiado para depois da fundacao backend
- .NET MAUI sera usado com foco inicial em iOS
- Android sera preservado como possibilidade futura, sem bloquear o primeiro ciclo mobile

### Infraestrutura local

- Docker
- PostgreSQL em container

## Dependencias entre projetos

As dependencias devem respeitar Clean Architecture.

```text
ProjetoEncontros.Api -> ProjetoEncontros.Aplicacao
ProjetoEncontros.Api -> ProjetoEncontros.Infraestrutura

ProjetoEncontros.Infraestrutura -> ProjetoEncontros.Aplicacao
ProjetoEncontros.Infraestrutura -> ProjetoEncontros.Dominio

ProjetoEncontros.Aplicacao -> ProjetoEncontros.Dominio

ProjetoEncontros.Dominio -> sem dependencia de projetos internos
```

O projeto `Dominio` nao deve depender de `Aplicacao`, `Infraestrutura`, `Api`, Entity Framework Core ou ASP.NET Core.

## Ordem recomendada de implementacao

### Etapa 1 - Criar estrutura da solucao

Objetivo:

- criar a solucao .NET e os projetos iniciais.

Entregas:

- solution criada
- projetos `Api`, `Aplicacao`, `Dominio`, `Infraestrutura`
- projetos de teste
- referencias entre projetos configuradas

Validacao:

- solucao compila sem codigo de negocio
- dependencias respeitam Clean Architecture

### Etapa 2 - Configurar API base

Objetivo:

- preparar a API para receber os primeiros endpoints.

Entregas:

- configuracao base do ASP.NET Core
- Swagger habilitado em desenvolvimento
- injecao de dependencia inicial
- tratamento padronizado de erros
- configuracao de autenticacao JWT

Validacao:

- API inicia localmente
- Swagger abre em desenvolvimento
- endpoint de health check ou rota simples responde, se adotado

### Etapa 3 - Configurar banco e Infraestrutura

Objetivo:

- conectar Entity Framework Core ao PostgreSQL.

Entregas:

- `DbContext`
- configuracao de connection string
- mapeamentos iniciais
- primeira migration
- Docker Compose para PostgreSQL local

Validacao:

- banco sobe localmente
- migration aplica com sucesso
- API consegue conectar ao banco

### Etapa 4 - Implementar dominio da fundacao

Objetivo:

- criar entidades e regras centrais da v0.1.

Entidades:

- `Usuario`
- `TokenDeAtualizacao`
- `Grupo`
- `MembroDoGrupo`
- `ConviteDoGrupo`

Value objects candidatos:

- `Email`
- `NomeDoGrupo`

Enums candidatos:

- `SituacaoDoUsuario`
- `SituacaoDoGrupo`
- `PapelDoMembroDoGrupo`
- `SituacaoDoMembroDoGrupo`
- `SituacaoDoConviteDoGrupo`

Validacao:

- regras de dominio testadas
- entidades nao dependem de infraestrutura

### Etapa 5 - Implementar autenticacao

Objetivo:

- permitir cadastro, login, refresh e logout.

Casos de uso:

- `CadastreUsuario`
- `AutentiqueUsuario`
- `RenoveSessao`
- `EncerreSessao`
- `ObtenhaUsuarioAtual`

Servicos necessarios:

- hash de senha
- geracao de JWT
- geracao de refresh token
- repositorio ou interface de persistencia de usuario
- repositorio ou interface de persistencia de refresh token

Endpoints:

```text
POST /api/autenticacao/cadastro
POST /api/autenticacao/login
POST /api/autenticacao/renovar-sessao
POST /api/autenticacao/sair
GET /api/usuarios/eu
```

Validacao:

- cadastro cria usuario
- login retorna tokens
- refresh token valido renova sessao
- logout revoga refresh token
- token invalido bloqueia acesso

### Etapa 6 - Implementar grupos

Objetivo:

- permitir criar, listar e visualizar grupos.

Casos de uso:

- `CrieGrupo`
- `ListeGruposDoUsuario`
- `ObtenhaDetalhesDoGrupo`

Endpoints:

```text
POST /api/grupos
GET /api/grupos
GET /api/grupos/{identificadorDoGrupo}
```

Regras essenciais:

- apenas usuario autenticado cria grupo
- criador vira dono
- grupo e privado por padrao
- apenas membros visualizam grupo

Validacao:

- usuario cria grupo
- grupo aparece na listagem do criador
- usuario externo nao acessa grupo

### Etapa 7 - Implementar convites

Objetivo:

- permitir entrada controlada em grupos privados.

Casos de uso:

- `CrieConviteDoGrupo`
- `ObtenhaDetalhesDoConvite`
- `AceiteConviteDoGrupo`
- `RecuseConviteDoGrupo`

Endpoints:

```text
POST /api/grupos/{identificadorDoGrupo}/convites
GET /api/convites
GET /api/convites/{identificadorDoConvite}
POST /api/convites/{identificadorDoConvite}/aceitar
POST /api/convites/{identificadorDoConvite}/recusar
```

Regras essenciais:

- apenas dono cria convite na v0.1
- convite inicia como pendente
- usuario convidado pode listar seus convites pendentes
- convite aceito cria membro
- convite aceito nao pode ser reutilizado
- convite nao deve expor dados sensiveis

Validacao:

- dono cria convite
- usuario convidado lista convite pendente
- usuario aceita convite valido
- usuario entra no grupo
- convite invalido nao permite entrada

### Etapa 8 - Implementar membros

Objetivo:

- permitir visualizacao e remocao basica de membros.

Casos de uso:

- `ListeMembrosDoGrupo`
- `RemovaMembroDoGrupo`

Endpoints:

```text
GET /api/grupos/{identificadorDoGrupo}/membros
DELETE /api/grupos/{identificadorDoGrupo}/membros/{identificadorDoMembro}
```

Regras essenciais:

- apenas membros visualizam lista
- apenas dono remove membro comum
- grupo nao pode ficar sem responsavel
- membro removido perde acesso ao grupo

Validacao:

- dono remove membro
- membro comum nao remove outro membro
- membro removido nao acessa grupo
- grupo nao fica sem dono

### Etapa 9 - Implementar testes automatizados

Objetivo:

- proteger regras criticas da fundacao.

Testes unitarios prioritarios:

- e-mail invalido
- nome de grupo invalido
- convite aceito nao pode ser aceito novamente
- membro duplicado no mesmo grupo deve ser bloqueado
- grupo deve manter responsavel

Testes de aplicacao prioritarios:

- cadastro com e-mail duplicado
- login com credenciais invalidas
- refresh token revogado
- criacao de grupo por usuario autenticado
- acesso negado a grupo externo
- aceite de convite valido
- remocao de membro sem permissao

Testes de integracao prioritarios:

- fluxo cadastro, login e criar grupo
- fluxo convite e aceite
- protecao de endpoint privado

### Etapa 10 - Revisar prontidao para cliente iOS

Objetivo:

- revisar se o backend esta pronto para ser consumido por um futuro cliente iOS.

Entregas:

- contratos de API revisados
- erros padronizados revisados
- fluxos principais testados via API
- decisoes pendentes do cliente iOS registradas

Fora do escopo:

- implementar telas mobile
- instalar workload MAUI
- criar projeto iOS

## Contratos iniciais de API

Os contratos abaixo sao conceituais e podem ser ajustados durante a implementacao.

### Cadastro

Request:

```json
{
  "nome": "Nome do Usuario",
  "email": "usuario@email.com",
  "senha": "senha"
}
```

Response:

```json
{
  "identificador": "identificador-do-usuario",
  "nome": "Nome do Usuario",
  "email": "usuario@email.com"
}
```

### Login

Request:

```json
{
  "email": "usuario@email.com",
  "senha": "senha"
}
```

Response:

```json
{
  "tokenDeAcesso": "jwt",
  "tokenDeAtualizacao": "token-de-atualizacao",
  "expiraEm": "2026-07-01T12:00:00Z"
}
```

### Criar grupo

Request:

```json
{
  "nome": "Amigos do Churrasco",
  "descricao": "Grupo para organizar nossos encontros"
}
```

Response:

```json
{
  "identificador": "identificador-do-grupo",
  "nome": "Amigos do Churrasco",
  "descricao": "Grupo para organizar nossos encontros",
  "papel": "Dono"
}
```

### Criar convite

Request:

```json
{
  "email": "convidado@email.com"
}
```

### Listar convites

Response:

```json
[
  {
    "identificador": "identificador-do-convite",
    "identificadorDoGrupo": "identificador-do-grupo",
    "nomeDoGrupo": "Amigos",
    "situacao": "Pendente",
    "criadoEm": "2026-07-01T12:00:00Z",
    "expiraEm": null
  }
]
```

Response:

```json
{
  "identificador": "identificador-do-convite",
  "identificadorDoGrupo": "identificador-do-grupo",
  "situacao": "Pendente"
}
```

## Padrao de erros

A API deve retornar erros padronizados.

Formato sugerido:

```json
{
  "codigo": "erro_de_validacao",
  "mensagem": "Existem dados invalidos na requisicao.",
  "detalhes": [
    {
      "campo": "email",
      "mensagem": "E-mail e obrigatorio."
    }
  ]
}
```

Diretrizes:

- nao expor detalhes internos
- mensagens devem ser claras
- erros de autenticacao nao devem revelar se e-mail existe
- erros de permissao devem ser consistentes

## Banco de dados

### Tabelas iniciais

- `usuarios`
- `tokens_de_atualizacao`
- `grupos`
- `membros_do_grupo`
- `convites_do_grupo`

### Relacionamentos

- `usuarios` 1:N `tokens_de_atualizacao`
- `usuarios` 1:N `grupos` como dono
- `grupos` 1:N `membros_do_grupo`
- `usuarios` 1:N `membros_do_grupo`
- `grupos` 1:N `convites_do_grupo`
- `usuarios` 1:N `convites_do_grupo` como usuario que convidou

### Restricoes importantes

- `usuarios.email` deve ser unico
- `membros_do_grupo` deve impedir duplicidade de usuario no mesmo grupo
- `convites_do_grupo` deve preservar estado do convite
- exclusoes devem evitar perda indevida de historico

## Seguranca

Regras tecnicas obrigatorias:

- senha com hash seguro
- JWT assinado
- refresh token revogavel
- endpoints privados protegidos
- validacao de pertencimento ao grupo em todos os endpoints privados de grupo
- logs sem senha, tokens ou dados sensiveis
- mensagens de erro sem vazamento de informacao

## Decisoes tecnicas que devem ser tomadas antes do codigo

As decisoes abaixo foram fechadas em `v0.1-decisoes-implementacao.md`:

- versao alvo do .NET: .NET 10 LTS
- nome fisico da solution: `ProjetoEncontros`
- tempo de expiracao do access token: 15 minutos
- tempo de expiracao do refresh token: 30 dias
- formato final dos IDs: Guid/UUID
- convite na v0.1: e-mail

- Docker Compose: sim, para PostgreSQL local

Ainda devem ser definidos durante a implementacao:

- estrategia exata de hash de senha

- biblioteca exata para assertions nos testes

## Riscos tecnicos da implementacao

### Misturar regras no controller

Mitigacao:

- controllers devem apenas receber request, chamar caso de uso e devolver response.

### Criar abstracoes demais

Mitigacao:

- usar interfaces e repositorios apenas onde ajudarem a separar aplicacao de infraestrutura.

### Falha de autorizacao por grupo

Mitigacao:

- todo caso de uso privado deve validar o usuario autenticado e sua participacao no grupo.

### Mobile duplicar regra do backend

Mitigacao:

- quando o cliente iOS for implementado, ele podera validar campos para usabilidade, mas a decisao final devera permanecer no backend.

### Escopo da v0.1 crescer

Mitigacao:

- bloquear encontros, memorias, notificacoes e midias ate versoes futuras.
