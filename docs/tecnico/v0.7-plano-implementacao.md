A primeira entrega tecnica da v0.7 deve focar em:

## Decisoes tecnicas da versao

### Pessoas frequentes como leitura derivada

Nao criar uma entidade obrigatoria `PessoaFrequente` na primeira entrega.

Decisao:

- pessoas frequentes serao calculadas a partir de encontros, participantes e convites existentes.

Motivo:

- reduz complexidade.
- evita criar uma agenda social paralela.
- preserva privacidade por encontro.
- permite validar utilidade antes de persistir curadoria manual.

Consequencia:

- a primeira consulta pode ser menos customizavel.
- remocao manual de sugestao fica para etapa futura, se necessaria.

### Convite continua explicito

Convite rapido nao adiciona participante automaticamente.

Decisao:

- o usuario precisa tocar na pessoa sugerida para convidar.
- o backend continua criando convite pelo fluxo oficial.

Motivo:

- preserva consentimento do organizador.
- impede que pessoas frequentes virem membros automaticos.
- evita vazamento de encontros privados.

### Tipo de encontro como campo simples

Tipo de encontro sera um campo opcional simples no encontro.

Decisao:

- usar texto controlado inicialmente, sem tabela complexa.
- limitar tamanho e normalizar entrada.
- nao alterar permissao nem comportamento central.

Motivo:

- entrega valor de organizacao sem overengineering.
- evita criar taxonomia definitiva antes de uso real.
- permite evoluir para entidade propria se houver necessidade.

### Modelos ficam fora da primeira entrega

Modelos de encontro nao entram na primeira implementacao tecnica.

Motivo:

- dependem de observar uso real.
- podem gerar criacao automatica confusa se forem apressados.
- a primeira melhoria de recorrencia deve ser convite rapido.

## Modelagem tecnica proposta

### PessoaFrequenteResposta

Contrato de leitura, nao entidade de dominio.

Campos:

- `IdentificadorDoUsuario`
- `Nome`
- `Email`
- `UrlDaFotoDePerfil`
- `QuantidadeDeEncontrosEmComum`
- `UltimoEncontroEm`

Regras:

- deve retornar apenas pessoas que participaram ou foram convidadas em encontros aos quais o usuario autenticado tem acesso.
- nao deve retornar o proprio usuario.
- deve ordenar por recorrencia e atividade recente.
- deve limitar quantidade para manter experiencia leve.

### TipoDoEncontro

Campo opcional em `Encontro`.

Nome sugerido:

- `Tipo`

Regras:

- opcional.
- maximo sugerido: 40 caracteres.
- deve ser normalizado com trim.
- string vazia deve ser tratada como `null`.
- nao altera permissao, presenca, convite ou memoria.

## Interfaces de aplicacao

### Consulta de pessoas frequentes

Criar caso de uso:

```text
ListePessoasFrequentes
```

Responsabilidades:

- validar usuario autenticado.
- consultar encontros acessiveis ao usuario.
- agrupar outros participantes por usuario.
- ordenar por frequencia e ultimo encontro.
- retornar lista limitada.

Possivel metodo no repositorio:

```text
ListePessoasFrequentesDoUsuarioAsync
```

O calculo deve ficar preferencialmente na infraestrutura quando depender de agregacao eficiente no banco.

## API

### Endpoint de pessoas frequentes

Criar rota privada:

```text

```

Comportamento:

- exige JWT.
- retorna sugestoes do usuario autenticado.
- nao aceita identificador de outro usuario.
- limita retorno.

Resposta:


## Riscos tecnicos

### Consulta pesada

Risco:

- calcular pessoas frequentes pode ficar caro com muitos encontros.

Mitigacao:

- limitar retorno.
- usar query agregada no banco.
- adicionar indices se necessario.
- evitar carregar todos os encontros em memoria.

### Vazamento de privacidade

Risco:

- sugerir pessoa com base em encontro que o usuario nao deveria acessar.

Mitigacao:

- partir sempre dos encontros acessiveis ao usuario.
- nunca aceitar identificador de usuario como filtro externo.
- testar usuario externo.

### Retorno ao problema dos grupos

Risco:

- sugestoes virarem participacao automatica.

Mitigacao:

- convite sempre explicito.
- nao criar permissao global.
- nao adicionar participante sem acao do usuario.

### Complexidade visual

Risco:

- tela de criacao de encontro ficar carregada.

Mitigacao:

- sugestoes compactas.
- tipo opcional discreto.
- esconder bloco quando nao houver sugestoes.
