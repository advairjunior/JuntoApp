# Projeto Encontros - Plano Tecnico de Implementacao - v0.4

## Objetivo do documento

Este documento define o plano tecnico para implementar a versao `0.4 - Organizacao Colaborativa` do Projeto Encontros.

## Escopo tecnico da v0.4

A versao `0.4` deve implementar combinados simples por encontro:

- criar item do encontro
- listar itens do encontro
- atribuir responsavel opcional
- remover responsavel, se a interface precisar
- marcar item como resolvido
- desfazer item resolvido
- preparar a area mobile de combinados

Lista simples e P0.

Responsavel e resolucao sao P1 dentro da versao, mas podem ser implementados no mesmo ciclo tecnico se a modelagem permanecer simples.

## Estado atual da base

A base atual ja possui:

- `Encontro` como agregado principal do produto

- presencas por encontro
- publicacoes por encontro

## Decisoes tecnicas da versao

### Item dentro do dominio de encontros

`ItemDoEncontro` deve ficar no dominio funcional `Encontros`.

Motivo:

- o item nao existe fora do contexto de um encontro
- permissoes dependem dos participantes do encontro
- evita criar uma area generica de tarefas no produto

### Repositorio proprio para itens

A aplicacao deve usar uma interface propria:

```text
IRepositorioDeItensDoEncontro
```

Motivo:

- evita aumentar ainda mais o repositorio de encontros
- deixa consultas de itens mais legiveis
- preserva simplicidade sem criar repositorio generico

### Estado simples

O item deve ter apenas dois estados iniciais:

- `Pendente`
- `Resolvido`

Motivo:

- reduz complexidade visual
- evita fluxo profissional de tarefas
- atende ao objetivo de combinados simples

### Responsavel opcional

O responsavel deve ser opcional.

Motivo:

- muitos combinados sao coletivos
- nao queremos obrigar cobranca social
- permite criar item rapidamente

## Modelagem de dominio

### ItemDoEncontro

Nova entidade no dominio `Encontros`.

Campos esperados:

- `Identificador`
- `IdentificadorDoEncontro`
- `Descricao`
- `IdentificadorDoUsuarioQueCriou`
- `IdentificadorDoUsuarioResponsavel`
- `Situacao`
- `AtualizadoEm`
- `CriadoEm`

Regras:

- item deve pertencer a um encontro
- item deve possuir usuario criador
- descricao deve ser obrigatoria
- descricao deve ter tamanho maximo inicial de 140 caracteres
- responsavel deve ser opcional
- item novo deve iniciar pendente
- item pendente pode ser marcado como resolvido
- item resolvido pode voltar para pendente
- item pode trocar responsavel
- item pode ficar sem responsavel

### SituacaoDoItemDoEncontro

Novo enum no dominio `Encontros`.

Valores:

- `Pendente`
- `Resolvido`

Regras:

- usar nome singular
- mapear como string no banco
- nao adicionar estados futuros sem necessidade real

## Casos de uso

### CrieItemDoEncontro

Objetivo:

- criar um combinado simples dentro de um encontro.

Validacoes:

- usuario autenticado deve ser participante do encontro
- encontro deve existir
- descricao deve ser obrigatoria
- descricao deve respeitar tamanho maximo
- responsavel, quando informado, deve ser participante do encontro

### ListeItensDoEncontro

Objetivo:

- listar combinados visiveis de um encontro.

Validacoes:

- usuario autenticado deve ser participante do encontro
- retornar apenas itens do encontro informado
- ordenar por situacao e criacao de forma previsivel

Ordem recomendada:

1. pendentes primeiro
2. resolvidos depois
3. dentro de cada grupo, mais recentes ou mais antigos conforme UX mobile confirmar

### AtribuaResponsavelAoItemDoEncontro

Objetivo:

- definir ou trocar o responsavel de um item.

Validacoes:

- usuario autenticado deve ser participante do encontro
- item deve pertencer ao encontro
- responsavel deve ser participante do encontro

### RemovaResponsavelDoItemDoEncontro

Objetivo:

- deixar item novamente sem responsavel.

Validacoes:

- usuario autenticado deve ser participante do encontro
- item deve pertencer ao encontro

### MarqueItemDoEncontroComoResolvido

Objetivo:

- marcar item como resolvido.

Validacoes:

- usuario autenticado deve ser participante do encontro
- item deve pertencer ao encontro
- item pendente pode ser resolvido
- chamada pode ser idempotente se o item ja estiver resolvido

### MarqueItemDoEncontroComoPendente

Objetivo:

- desfazer resolucao do item.

Validacoes:

- usuario autenticado deve ser participante do encontro
- item deve pertencer ao encontro
- item resolvido pode voltar para pendente
- chamada pode ser idempotente se o item ja estiver pendente

## Contratos de aplicacao

Contratos esperados:

- `CrieItemDoEncontroComando`
- `AtribuaResponsavelAoItemDoEncontroComando`
- `RemovaResponsavelDoItemDoEncontroComando`
- `MarqueItemDoEncontroComoResolvidoComando`
- `MarqueItemDoEncontroComoPendenteComando`

Os contratos devem usar portugues e expor apenas dados necessarios ao mobile.

## Contratos de API

### Criar item do encontro

Rota:

```text
POST /api/encontros/{identificadorDoEncontro}/itens
```

Corpo:

```json
{
  "descricao": "Levar refrigerante",
  "identificadorDoUsuarioResponsavel": "guid opcional"
}
```

Resposta:

```json
{
  "identificador": "guid",
  "identificadorDoEncontro": "guid",
  "descricao": "Levar refrigerante",
  "nomeDoUsuarioQueCriou": "Deborah",
  "identificadorDoUsuarioResponsavel": "guid",
  "nomeDoUsuarioResponsavel": "Advair",
  "situacao": "Pendente",
  "atualizadoEm": "2026-07-13T12:00:00Z",
  "criadoEm": "2026-07-13T12:00:00Z"
}
```

### Listar itens do encontro

Rota:

```text
GET /api/encontros/{identificadorDoEncontro}/itens
```

Resposta:

```json
[
  {
    "identificador": "guid",
    "identificadorDoEncontro": "guid",
    "descricao": "Levar refrigerante",
    "nomeDoUsuarioQueCriou": "Deborah",
    "identificadorDoUsuarioResponsavel": "guid",
    "nomeDoUsuarioResponsavel": "Advair",
    "situacao": "Pendente",
    "atualizadoEm": "2026-07-13T12:00:00Z",
    "criadoEm": "2026-07-13T12:00:00Z"
  }
]
```

### Atribuir responsavel

Rota:

```text
PUT /api/encontros/{identificadorDoEncontro}/itens/{identificadorDoItem}/responsavel
```

Corpo:

```json
{
  "identificadorDoUsuarioResponsavel": "guid"
}
```

Resposta:

```text
200 OK
```

com `ItemDoEncontroResposta`.

### Remover responsavel

Rota:

```text
DELETE /api/encontros/{identificadorDoEncontro}/itens/{identificadorDoItem}/responsavel
```

Resposta:

```text
200 OK
```

com `ItemDoEncontroResposta`.

### Marcar como resolvido

Rota:

```text
POST /api/encontros/{identificadorDoEncontro}/itens/{identificadorDoItem}/resolver
```

Resposta:

```text
200 OK
```

com `ItemDoEncontroResposta`.

### Marcar como pendente

Rota:

```text
POST /api/encontros/{identificadorDoEncontro}/itens/{identificadorDoItem}/pendente
```

Resposta:

```text
200 OK
```

com `ItemDoEncontroResposta`.

## Regras de autorizacao

Todo endpoint de item deve:

- exigir JWT
- validar usuario autenticado
- validar participante ativo do encontro
- validar que o item pertence ao encontro informado
- retornar acesso negado generico quando o usuario nao tiver acesso

Recursos privados inacessiveis devem seguir `DT-004`.

### UX mobile

Diretrizes:

- estado vazio deve convidar a adicionar o primeiro combinado

- item resolvido deve continuar acessivel
- erro de criacao deve ser curto e humano
- acao principal deve ficar ao alcance do polegar

## Riscos tecnicos

### Repositorio de itens duplicar regra de permissao

Risco:

- permissao de participante ser reimplementada de forma inconsistente.

Mitigacao:

- manter validacao de participante usando a mesma fonte dos fluxos de encontro.

### Tela do encontro ficar cheia demais

Risco:

- combinados, mensagens, midias e presencas competirem na mesma tela.

Mitigacao:

- usar tela propria para combinados e entrada discreta no detalhe/informacoes.

### Modelagem virar generica demais

Risco:

- criar uma entidade de tarefa generica antes da necessidade.

Mitigacao:

- manter nome e comportamento como `ItemDoEncontro`.

## Criterios tecnicos de pronto

A implementacao da v0.4 deve ser considerada pronta quando:

- solution compilar
- testes automatizados passarem
- migration aplicar corretamente
- Swagger exibir endpoints de itens
- endpoints exigirem JWT
- autorizacao por participante funcionar
- usuario externo nao acessar itens
- item valido for criado e listado
- item invalido for rejeitado
- responsavel externo for rejeitado
- item puder ser resolvido e voltar para pendente
- app mobile permitir visualizar e criar combinados
- estados de vazio, carregamento e erro existirem no mobile

- Testes automatizados validados: 147 testes unitarios e 22 testes de integracao passando.
- Documento de QA da v0.4 criado em `v0.4-qa.md`.
