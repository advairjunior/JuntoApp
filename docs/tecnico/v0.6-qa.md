## Ajustes aplicados apos revisao dos agentes

Durante a Etapa 7, os agentes de QA, Produto e Mobile apontaram divergencias relevantes. Foram aplicados os seguintes ajustes antes de registrar esta validacao:

- rotas legadas de encontro de grupo tambem notificam participantes em edicao e cancelamento.
- testes unitarios existentes de edicao e cancelamento de encontro de grupo passaram a validar notificacao para outro participante.

  - `ConviteRecebido`
  - `NovoEncontro`
  - `AlteracaoDeEncontro`
  - `ItemSobResponsabilidade`
  - `LembreteDeEncontro`
- tela de detalhes do encontro separa `401 Unauthorized` de `403 Forbidden`.
- `403 Forbidden` nao limpa mais a sessao na carga inicial do detalhe do encontro.
- tela de notificacoes recarrega ao reaparecer, reduzindo risco de contador ou estado de leitura desatualizado.
- estado vazio da tela de notificacoes nao aparece junto com mensagem de erro.
- mensagem de sucesso das preferencias ganhou visual semantico de sucesso, nao de erro.
- largura principal das telas refinadas passou a usar largura maxima flexivel.
- escopo de produto reconciliado: lembrete automatico antes do encontro foi movido para subversao futura.

## Casos de teste manuais

### QA-06-001 - Receber convite e visualizar notificacao

Objetivo:

- garantir que um usuario convidado perceba o convite pela central de notificacoes.

Pre-condicoes:

- usuario A autenticado.
- usuario B existente.
- usuario A cria encontro e convida usuario B.

Passos:

1. Entrar como usuario B.
2. Abrir a Home.
3. Verificar o sino com badge.
4. Abrir `Notificacoes`.
5. Tocar na notificacao de convite.

Resultado esperado:

- notificacao aparece para usuario B.
- notificacao nao aparece para usuario diferente.
- ao tocar, o app abre o encontro relacionado.
- notificacao fica lida apos abertura.

Prioridade: P0

Tipo: funcional

### QA-06-002 - Alteracao de encontro gera notificacao

Objetivo:

- garantir que participantes sejam avisados quando um encontro muda.

Pre-condicoes:

- encontro com pelo menos dois participantes.
- usuario organizador autenticado.

Passos:

1. Editar data, horario ou local do encontro.
2. Entrar como participante.
3. Abrir notificacoes.

Resultado esperado:

- participante recebe notificacao de alteracao.
- organizador que executou a acao nao recebe notificacao duplicada.
- toque abre o encontro atualizado.

Prioridade: P0

Tipo: funcional

### QA-06-003 - Preferencias bloqueiam notificacoes futuras

Objetivo:

- garantir que preferencias simples sejam respeitadas.

Pre-condicoes:

- usuario autenticado.
- tela de preferencias acessivel pelo Perfil.

Passos:

1. Desativar notificacoes de combinados.
2. Salvar preferencias.
3. Em outro usuario, atribuir um combinado ao usuario testado.
4. Abrir notificacoes do usuario testado.

Resultado esperado:

- nova notificacao de combinado nao deve ser criada para o usuario que desativou esse tipo.
- demais tipos ativos continuam funcionando.

Prioridade: P1

Tipo: regra de negocio

### QA-06-004 - Estado vazio da central

Objetivo:

- garantir que a tela nao pareca erro quando nao ha atividades.

Pre-condicoes:

- usuario autenticado sem notificacoes.

Passos:

1. Abrir a Home.
2. Abrir `Notificacoes`.

Resultado esperado:

- tela exibe estado vazio com texto amigavel.
- nao ha alerta agressivo.
- nao ha preferencia misturada na central.

Prioridade: P1

Tipo: UX

### QA-06-005 - API indisponivel

Objetivo:

- validar comportamento quando a API ou banco nao respondem.

Pre-condicoes:

- aplicativo aberto.
- API ou PostgreSQL parado.

Passos:

1. Abrir a Home.
2. Abrir `Notificacoes`.
3. Abrir preferencias de notificacao.

Resultado esperado:

- usuario recebe mensagem curta de erro.
- estado vazio nao aparece junto com erro.
- app nao fecha inesperadamente.

Prioridade: P1

Tipo: resiliencia

## Analise dos agentes

### Product Owner

Valor validado:

- notificacoes essenciais reduzem esquecimentos e ajudam o usuario a acompanhar convites, alteracoes e responsabilidades.
- a versao preserva a identidade do produto porque evita notificacoes artificiais de engajamento.
- preferencias simples dao controle ao usuario sem transformar a tela em painel complexo.

### Software Architect

Pontos validados:

- notificacoes permanecem privadas por usuario.
- criacao fica centralizada no servico de aplicacao.
- dominio nao depende de API, EF Core ou MAUI.
- push real continua fora do escopo, evitando complexidade prematura.

### Senior Backend

Pontos validados:

- contratos da API estao protegidos por JWT.
- repositories e migration foram adicionados.
- testes de integracao cobrem os endpoints principais.
- PostgreSQL local e necessario para executar a suite de integracao.

### Mobile Specialist

Pontos incorporados antes deste QA:

- tela de notificacoes ficou focada em atividades, nao em configuracoes.
- preferencias foram movidas para tela separada.
- icone de alerta textual foi substituido por sino.
- estado vazio nao deve aparecer junto de erro.
- tela de notificacoes recarrega ao reaparecer para refletir leitura.
- largura principal das telas passou a respeitar `MaximumWidthRequest` sem largura fixa obrigatoria.

### UI/UX Designer

Pontos validados:

- notificacoes agora possuem hierarquia mais proxima de uma central de atividades.
- preferencias ficam no Perfil, que e o local mental esperado para configuracoes.
- estados vazios e badges devem ser discretos para nao parecerem alarme.

### QA Engineer

Foco aplicado:

- validar permissao, privacidade, estado vazio, erro, leitura, preferencias e regressao da Home.
- nao assumir que a funcionalidade esta pronta apenas por compilar.
- manter validacao manual obrigatoria antes do fechamento oficial.
