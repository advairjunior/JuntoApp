## Escopo tecnico da v0.6

A versao `0.6` deve implementar notificacoes internas essenciais:

- criar notificacoes privadas por usuario
- listar notificacoes do usuario autenticado
- marcar notificacao como lida
- exibir quantidade de notificacoes nao lidas
- criar notificacoes em eventos importantes de encontro
- salvar preferencias simples de notificacao
- preparar a arquitetura para push notification futura sem implementar APNs agora

O nucleo P0 e a notificacao interna privada.

Push notification real fica fora da primeira implementacao tecnica da v0.6.

## Decisoes tecnicas da versao

### Notificacao interna persistida

Criar uma entidade persistida para notificacoes do usuario.

Motivo:

- notificacao precisa sobreviver ao fechamento do app
- usuario pode consultar historico curto
- backend consegue contar nao lidas
- push futura podera reutilizar o mesmo registro como origem

### Notificacao pertence ao usuario

Toda notificacao deve ter `IdentificadorDoUsuario`.

Motivo:

- simplifica privacidade
- evita listagem por encontro expondo dados indevidos
- garante que a API sempre consulte notificacoes do usuario autenticado

### Preferencias simples persistidas

Criar preferencias por usuario.

Motivo:

- usuario deve controlar interrupcoes
- configuracao deve sobreviver ao login
- futuras notificacoes push poderao respeitar a mesma regra

### Sem push externa nesta etapa

Nao implementar APNs, FCM ou registro definitivo de dispositivo na primeira entrega.

Motivo:

- exige ambiente Apple, certificados e permissao do sistema
- aumenta risco tecnico sem validar antes a regra de produto
- pode ser tratado em subversao futura com base interna pronta

### Geracao por servico de aplicacao

Notificacoes devem ser criadas por um servico de aplicacao, nao diretamente por rotas ou telas.

Motivo:

- centraliza regras de preferencia
- reduz duplicacao
- facilita testes
- prepara envio externo futuro

## Modelagem de dominio

### NotificacaoDoUsuario

Entidade sugerida no dominio:

```text
NotificacaoDoUsuario
```

Propriedades:

- `Identificador`
- `IdentificadorDoUsuario`
- `Tipo`
- `Titulo`
- `Mensagem`
- `IdentificadorDoEncontro`
- `IdentificadorDoConvite`
- `IdentificadorDoItem`
- `Situacao`
- `CriadaEm`
- `LidaEm`

Metodos esperados:

- criar notificacao
- marque como lida
- verifique se esta lida

Regras:

- titulo e mensagem devem ser obrigatorios
- notificacao deve ter usuario dono
- notificacao inicia como nao lida
- notificacao lida deve registrar data de leitura
- marcar como lida novamente nao deve quebrar o fluxo

### PreferenciaDeNotificacaoDoUsuario

Entidade sugerida no dominio:

```text
PreferenciaDeNotificacaoDoUsuario
```

Propriedades:

- `IdentificadorDoUsuario`
- `NotificacoesDeConviteAtivas`
- `LembretesDeEncontroAtivos`
- `NotificacoesDeAlteracaoAtivas`
- `NotificacoesDeCombinadosAtivas`
- `AtualizadaEm`

Regras:

- preferencias padrao devem vir ativas para notificacoes essenciais
- usuario pode alterar apenas as proprias preferencias
- ausencia de registro deve ser tratada como preferencia padrao

## Casos de uso

### ListeNotificacoesDoUsuario

Objetivo:

- listar notificacoes do usuario autenticado.

Fluxo:

1. validar usuario autenticado.
2. buscar notificacoes do usuario.
3. buscar quantidade nao lida.
4. retornar resposta.

### MarqueNotificacaoComoLida

Objetivo:

- marcar notificacao do usuario como lida.

Fluxo:

1. validar usuario autenticado.
2. buscar notificacao pelo identificador e usuario.
3. marcar como lida.
4. salvar alteracao.

### ObtenhaPreferenciasDeNotificacao

Objetivo:

- retornar preferencias do usuario.

Fluxo:

1. validar usuario autenticado.
2. buscar preferencias.
3. retornar registro existente ou padrao.

### AtualizePreferenciasDeNotificacao

Objetivo:

- atualizar preferencias simples do usuario.

Fluxo:

1. validar usuario autenticado.
2. validar requisicao.
3. criar ou atualizar preferencias.
4. retornar preferencias atualizadas.

## Pontos de geracao de notificacoes

### Convite para encontro

Quando:

- participante for convidado para um encontro.

Quem recebe:

- usuario convidado, se houver usuario associado ao e-mail.

Tipo:

- `ConviteRecebido`

### Novo encontro

Quando:

- encontro for criado com participantes definidos, quando o fluxo permitir.

Quem recebe:

- participantes convidados, exceto organizador que criou o encontro.

Tipo:

- `NovoEncontro`

### Alteracao de encontro

Quando:

- data, horario, local ou cancelamento mudar.

Quem recebe:

- participantes ativos do encontro, exceto usuario que realizou a alteracao.

Tipo:

- `AlteracaoDeEncontro`

### Item sob responsabilidade

Quando:

- item de combinado for atribuido a um usuario.

Quem recebe:

- usuario responsavel.

Tipo:

- `ItemSobResponsabilidade`

### Lembrete de encontro

Quando:

- houver mecanismo de processamento agendado.

Quem recebe:

- participantes ativos com lembrete habilitado.

Tipo:

- `LembreteDeEncontro`

Decisao da primeira entrega:

- registrar a regra e preparar o contrato, mas implementar lembrete automatico apenas se houver mecanismo simples e testavel sem infraestrutura externa.

## API

### Listar notificacoes

```text
GET /api/notificacoes
```

Resposta:

```json
{
  "quantidadeNaoLida": 2,
  "notificacoes": [
    {
      "identificador": "guid",
      "tipo": "ConviteRecebido",
      "titulo": "Voce foi convidado",
      "mensagem": "Deborah convidou voce para Resenha do ADVA.",
      "identificadorDoEncontro": "guid",
      "identificadorDoConvite": "guid",
      "identificadorDoItem": null,
      "situacao": "NaoLida",
      "criadaEm": "2026-07-13T12:00:00Z",
      "lidaEm": null

  ]
```

## Riscos tecnicos

### Notificacao duplicada

Risco:

- a mesma acao gerar varias notificacoes iguais.

Mitigacao:

- centralizar criacao em `IServicoDeNotificacoes`
- testar fluxos principais
- evitar gerar notificacao em camadas diferentes

### Vazamento de dados

Risco:

- usuario acessar notificacao ou destino de outro usuario.

Mitigacao:

- filtrar sempre por `IdentificadorDoUsuario`
- validar acesso ao destino no caso de uso original
- criar testes de integracao com usuario externo

### Escopo crescer para push real

Risco:

- a v0.6 travar por dependencia de Apple, certificado ou ambiente externo.

Mitigacao:

- manter push real fora da primeira entrega
- preparar interfaces, mas entregar valor com notificacao interna

### Lembrete automatico fora da primeira entrega

Nao implementar processamento agendado de lembretes antes do encontro na primeira entrega tecnica da v0.6.

Motivo:

- exige decisao de agendador, janela temporal, idempotencia e execucao em segundo plano.
- nao deve travar a entrega da central interna de notificacoes.
- o tipo `LembreteDeEncontro` e a preferencia ficam preparados para subversao futura.
