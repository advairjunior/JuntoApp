# Projeto Encontros - Plano de Transicao Tecnica - v0.2.3

## Objetivo do documento

Este documento define o plano tecnico para transicionar o Projeto Encontros de uma arquitetura centrada em `Grupo` para uma arquitetura centrada em `Encontro`.

A `v0.2.3` nao deve apagar tudo que ja foi feito. Ela deve preservar o que e aproveitavel e corrigir a dependencia estrutural errada: encontros nao devem depender de grupos para existir, aparecer ou controlar privacidade.

## Diagnostico do estado atual

O codigo atual esta centrado em `Grupo`.

Pontos principais:

- `Encontro` possui `IdentificadorDoGrupo`
- `PresencaNoEncontro` aponta para `MembroDoGrupo`
- rotas de encontros estao aninhadas em `/api/grupos/{identificadorDoGrupo}/encontros`
- a tela inicial mobile prioriza grupos
- a tela de detalhe do grupo concentra encontros
- o banco possui FK obrigatoria de `encontros` para `grupos`

Essa estrutura funcionou para validar a fundacao, mas nao representa o produto final desejado.

## Decisao tecnica principal

`Encontro` passa a ser o agregado principal da experiencia.

`ParticipanteDoEncontro` deve concentrar:

- convite
- acesso ao encontro
- papel no encontro
- resposta de presenca
- autorizacao para ver mural e midias

Isso evita manter `ConvidadoDoEncontro` e `PresencaNoEncontro` como duas fontes de verdade.

## Modelo alvo

```text
Encontro
  ParticipantesDoEncontro
    Usuario
    Papel
    Situacao
    ConvidadoEm
    RespondidoEm
  PublicacoesDoEncontro
  MidiasDoEncontro
```

`Grupo` ou `Turma` pode existir no futuro como apoio, mas nao como fronteira obrigatoria de privacidade.

## Entidades alvo

### Encontro

Campos esperados no modelo alvo:

- `Identificador`
- `Titulo`
- `Descricao`
- `Local`
- `InicioEm`
- `IdentificadorDoUsuarioQueCriou`
- `IdentificadorDaTurmaOrigem` opcional
- `Situacao`
- `CriadoEm`
- `AtualizadoEm`

Regras:

- encontro pode existir sem grupo
- encontro sempre tem criador
- criador sempre e participante
- somente participantes autorizados visualizam o encontro
- encontro cancelado nao aceita novas presencas
- encontro realizado sera usado futuramente para memorias

### ParticipanteDoEncontro

Campos esperados:

- `Identificador`
- `IdentificadorDoEncontro`
- `IdentificadorDoUsuario`
- `Papel`
- `Situacao`
- `ConvidadoEm`
- `RespondidoEm`

Papeis iniciais:

- `Organizador`
- `Convidado`

Situacoes iniciais:

- `Convidado`
- `Confirmado`
- `Talvez`
- `NaoVai`
- `Removido`

Regras:

- mesmo usuario nao pode participar duas vezes do mesmo encontro
- organizador nao pode ser removido sem regra futura de transferencia
- usuario removido nao acessa mais o encontro
- usuario nao convidado nao sabe que o encontro existe
- presenca e resposta do participante, nao entidade separada no modelo alvo

## Estrategia incremental

### Fase 1 - Documentacao oficial

Atualizar documentos de produto para declarar `Encontro` como centro:

- `00-visao-produto.md`
- `01-roadmap-versoes.md`
- `03-regras-de-produto.md`
- `04-backlog-inicial.md`
- `02-arquitetura-inicial.md`

Registrar decisao tecnica nova em `decisoes-tecnicas.md`.

### Fase 2 - Dominio

Implementar:

- `ParticipanteDoEncontro`
- `PapelDoParticipanteDoEncontro`
- `SituacaoDoParticipanteDoEncontro`
- metodos em `Encontro` para convidar, confirmar, marcar talvez, recusar e remover participante
- criador como participante organizador automatico

Manter `PresencaNoEncontro` temporariamente apenas se necessario para compatibilidade, mas nao expandir seu uso.

### Fase 3 - Banco

Criar tabela:

- `participantes_do_encontro`

Relacionamentos:

- `encontros` 1:N `participantes_do_encontro`
- `usuarios` 1:N `participantes_do_encontro`

Restricoes:

- unico por `identificador_do_encontro` e `identificador_do_usuario`
- indice por `identificador_do_usuario`, `situacao`
- indice por `identificador_do_encontro`, `situacao`

Migração de dados existentes:

- para cada encontro existente, criar participante organizador para `IdentificadorDoUsuarioQueCriou`
- para cada presenca existente, criar ou atualizar participante correspondente ao usuario do `MembroDoGrupo`
- para preservar comportamento antigo em desenvolvimento, adicionar membros ativos do grupo como participantes convidados dos encontros existentes

Depois:

- tornar `encontros.identificador_do_grupo` opcional ou manter temporariamente como origem
- nao remover tabelas de grupo nesta fase

### Fase 4 - Aplicacao

Criar novos casos de uso ou adaptar os existentes para operar por encontro:

- `CrieEncontro`
- `ListeEncontrosDoUsuario`
- `ObtenhaDetalhesDoEncontro`
- `EditeEncontro`
- `CanceleEncontro`
- `RespondaPresencaNoEncontro`
- `ListeParticipantesDoEncontro`

Regras:

- nao iniciar caso de uso de encontro buscando grupo
- validar acesso pelo participante do encontro
- preservar acesso negado generico conforme `DT-004`

### Fase 5 - API

Criar rotas canonicas:

```text
POST /api/encontros
GET /api/encontros
GET /api/encontros/proximos
GET /api/encontros/passados
GET /api/encontros/{identificadorDoEncontro}
PUT /api/encontros/{identificadorDoEncontro}
POST /api/encontros/{identificadorDoEncontro}/cancelar
POST /api/encontros/{identificadorDoEncontro}/presenca
DELETE /api/encontros/{identificadorDoEncontro}/presenca
GET /api/encontros/{identificadorDoEncontro}/participantes
```

Rotas antigas:

```text
/api/grupos/{identificadorDoGrupo}/encontros
```

devem ficar temporariamente como compatibilidade ou ser removidas apenas quando o mobile deixar de depender delas.

### Fase 6 - Mobile

Alterar a navegacao principal:

Antes:

```text
Inicio -> Grupos -> Detalhe do grupo -> Encontros
```

Depois:

```text
Inicio -> Encontros -> Detalhe do encontro
```

Tela inicial:

- Hoje
- Convites pendentes
- Esta semana
- Este mes
- Passados
- Relembrar encontros

Criacao:

- criar encontro direto pelo botao principal
- escolher convidados por e-mail ou pessoas recentes, conforme decisao tecnica da fase
- nao exigir grupo antes

Detalhe:

- dados do encontro
- participantes
- presenca
- mural do encontro
- midias do encontro

### Fase 7 - Depreciar grupo

Depois que encontros estiverem independentes:

- remover grupo da navegacao principal
- manter grupo/turma apenas se houver valor para sugestao de pessoas
- decidir se codigo sera renomeado ou se grupo sera mantido como recurso secundario

## Decisoes importantes

### Grupo sera removido agora?

Nao.

Remover grupo imediatamente aumenta risco sem necessidade.

Grupo deve perder centralidade primeiro. Depois sera decidido se vira `Turma`, recurso de pessoas frequentes ou se sera removido.

### Presenca continua como entidade separada?

No modelo alvo, nao.

Presenca deve ser estado do `ParticipanteDoEncontro`.

Durante a transicao, a entidade atual pode permanecer para compatibilidade ate a migracao estar segura.

### Mural e midias entram agora?

Nao na primeira fase tecnica da transicao.

Primeiro corrigir:

- encontro independente
- participantes
- privacidade
- tela inicial centrada em encontros

Depois implementar mural e midias.

## Riscos

### Privacidade parcial

Se alguns fluxos ainda validarem por grupo, encontros podem vazar.

Mitigacao:

Todos os casos de uso novos devem validar participante do encontro.

### Migration complexa

Converter presencas baseadas em membros do grupo para participantes por usuario pode falhar.

Mitigacao:

Criar testes de integracao cobrindo dados antigos.

### Mobile quebrar navegacao

Mobile atual depende de `IdentificadorDoGrupo`.

Mitigacao:

Criar rotas novas antes de remover antigas.

### Escopo crescer demais

Mural, midias, convites externos e pessoas recentes podem crescer juntos.

Mitigacao:

Primeira transicao deve focar apenas no eixo principal: encontro, participantes, listagem e presenca.

## Criterios de pronto da v0.2.3

- Usuario consegue criar encontro sem criar grupo antes.
- Criador vira participante organizador automaticamente.
- Usuario convidado visualiza o encontro.
- Usuario nao convidado nao visualiza nem acessa detalhe.
- Tela inicial mostra encontros, nao grupos.
- Convites e presencas pertencem ao encontro.
- Rotas canonicas `/api/encontros` existem.
- Rotas antigas de grupo nao sao mais usadas pelo mobile principal.
- Testes cobrem privacidade por participante.
- Documentacao oficial deixa claro que `Encontro` e o centro do produto.

## Status de implementacao

### Concluido

- Criacao direta de encontro em `/api/encontros`.
- Criador como participante organizador automatico.
- Participantes do encontro como base para acesso, convite e presenca.
- Listagem de encontros do usuario centrada em `/api/encontros`.
- Convites pendentes de encontro em `/api/encontros/convites`.
- Mobile usando convites pendentes de encontro na tela inicial.
- Aceite e recusa de convite de encontro respondendo a presenca do participante.
- Convites pendentes nao aparecem duplicados em `Proximos encontros`.
- Mural privado de texto do encontro, com publicacao e listagem restritas aos participantes.
- Historico basico de encontros passados em `/api/encontros/passados` e aba `Memorias` no mobile.

### Ainda pendente

- Midias do encontro.
- Album de memorias com fotos/videos dos encontros passados.
- Sugestoes de pessoas recentes.
- Depreciacao visual completa das areas antigas de grupo.
