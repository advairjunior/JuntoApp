## Contratos de API disponiveis

### Saude

```text
GET /
GET /api/saude
```

Objetivo:

- permitir validacao simples de que a API esta executando.

### Autenticacao

```text
POST /api/autenticacao/cadastro
POST /api/autenticacao/login
POST /api/autenticacao/renovar-sessao
POST /api/autenticacao/sair
```

Status HTTP esperados:

- `201 Created` para cadastro valido
- `200 OK` para login valido
- `200 OK` para renovacao valida
- `204 No Content` para logout valido
- `400 Bad Request` para dados invalidos ou regra rejeitada

Observacoes para iOS:

- o app devera guardar access token e refresh token com armazenamento seguro do iOS
- o access token expira em 15 minutos
- o refresh token expira em 30 dias
- o logout deve enviar o refresh token para revogacao

### Usuario atual

```text
GET /api/usuarios/eu
```

Status HTTP esperados:

- `200 OK` para usuario autenticado
- `401 Unauthorized` para access token ausente ou invalido
- `403 Forbidden` para acesso negado por regra da aplicacao

Observacoes para iOS:

- este endpoint deve ser usado para validar a sessao ao abrir o app
- o app nao deve confiar apenas na existencia local de token

### Grupos

```text
POST /api/grupos
GET /api/grupos
GET /api/grupos/{identificadorDoGrupo}
```

Status HTTP esperados:

- `201 Created` para criacao valida
- `200 OK` para listagem e detalhe
- `400 Bad Request` para dados invalidos
- `401 Unauthorized` para usuario nao autenticado
- `403 Forbidden` para usuario sem acesso ao grupo

Observacoes para iOS:

- a tela inicial autenticada pode usar `GET /api/grupos`
- grupos vazios devem gerar estado vazio simples
- usuario externo nao deve visualizar grupos de terceiros

### Convites

```text
GET /api/convites
POST /api/grupos/{identificadorDoGrupo}/convites
GET /api/convites/{identificadorDoConvite}
POST /api/convites/{identificadorDoConvite}/aceitar
POST /api/convites/{identificadorDoConvite}/recusar
```

Status HTTP esperados:

- `200 OK` para listagem de convites pendentes
- `201 Created` para convite criado
- `200 OK` para detalhe, aceite e recusa
- `400 Bad Request` para dados invalidos ou convite em estado invalido
- `401 Unauthorized` para usuario nao autenticado
- `403 Forbidden` para usuario sem acesso ao convite

Observacoes para iOS:

- na `v0.1`, convite continua vinculado ao e-mail da conta
- `GET /api/convites` retorna a lista de convites pendentes do usuario autenticado
- lista vazia deve ser tratada pelo app como ausencia de convites pendentes
- o convite nao deve expor dados sensiveis do grupo
- o usuario autenticado deve ser o destinatario do convite para visualizar, aceitar ou recusar
- compartilhamento por WhatsApp deve ser tratado como melhoria futura, nao como requisito da `v0.1`

### Membros

```text
GET /api/grupos/{identificadorDoGrupo}/membros
DELETE /api/grupos/{identificadorDoGrupo}/membros/{identificadorDoMembro}
```

Status HTTP esperados:

- `200 OK` para listagem
- `204 No Content` para remocao valida
- `400 Bad Request` para regra rejeitada
- `401 Unauthorized` para usuario nao autenticado
- `403 Forbidden` para usuario sem permissao

Observacoes para iOS:

- lista de membros nao retorna e-mail na `v0.1`
- o app deve usar `EhUsuarioAtual` para destacar o usuario logado
- remocao deve ser exibida apenas quando a experiencia validar permissao esperada
- o backend continua sendo a fonte final da permissao

## Padrao de erro

A API possui tratamento padronizado para erros de dominio, aplicacao, acesso negado e erro interno.

Formato base:

```json
{
  "codigo": "erro_de_aplicacao",
  "mensagem": "Mensagem clara para o usuario."
}
```

Diretrizes para iOS:

- mostrar mensagens de erro de forma simples
- nao tentar interpretar mensagens internas como regra de interface permanente
- tratar `401` como sessao ausente ou token invalido
- tratar `403` como acao nao permitida
- tratar `400` como dados invalidos ou regra de negocio rejeitada
- para recursos privados inexistentes ou inacessiveis, a API pode retornar `403` para evitar vazamento de existencia

## Fluxos principais para o primeiro cliente iOS

### Primeiro acesso

1. Usuario abre o app.
2. App verifica se possui tokens guardados.
3. Se nao houver tokens, mostra entrada ou cadastro.
4. Se houver tokens, chama `GET /api/usuarios/eu`.
5. Se o access token estiver expirado, chama `POST /api/autenticacao/renovar-sessao`.
6. Se a renovacao falhar, volta para login.

### Criacao do primeiro grupo

1. Usuario autenticado acessa lista de grupos.
2. Se nao houver grupos, app mostra estado vazio com acao para criar grupo.
3. Usuario cria grupo.
4. Backend registra o usuario como dono.
5. App abre detalhe basico do grupo.

### Convite por e-mail

1. Dono acessa grupo.
2. Dono cria convite informando e-mail.
3. Backend cria convite pendente.
4. Pessoa convidada autentica com o mesmo e-mail.
5. App chama `GET /api/convites`.
6. App mostra convites pendentes do usuario.
7. Pessoa convidada visualiza, aceita ou recusa convite.
8. Ao aceitar, passa a ser membro do grupo.

### Remocao de membro

1. Dono acessa lista de membros.
2. Dono escolhe membro comum.
3. Backend remove logicamente o membro.
4. Membro removido perde acesso ao grupo.

Diretrizes:

- validar iOS primeiro
- nao prometer Android no primeiro ciclo mobile
- manter componentes reutilizaveis
- revisar a decisao se o spike mobile falhar

### Autenticacao no app

Definir:

- armazenamento seguro dos tokens
- estrategia de renovacao silenciosa
- comportamento quando refresh token expirar
- comportamento quando usuario fizer logout

### Navegacao inicial

Definir:

- tela de entrada
- tela de cadastro
- tela de grupos
- tela de grupo
- tela de convite
- tela de membros

### Compartilhamento de convite

O WhatsApp deve ser considerado canal de compartilhamento futuro, nao integracao obrigatoria da `v0.1`.

Direcao recomendada:

- manter convite por e-mail na `v0.1`
- em versao futura, gerar experiencia de "Compartilhar pelo WhatsApp"
- o aceite deve continuar protegido por identidade, expiracao, revogacao ou outro controle equivalente
- evitar link publico sem controle

## Riscos para o cliente iOS

### Sessao mal armazenada

Risco:

- tokens salvos de forma insegura no dispositivo.

Mitigacao:

- usar armazenamento seguro nativo do iOS.

### Interface assumir permissao que o backend nao garante

Risco:

- app mostrar acoes que o usuario nao pode executar.

Mitigacao:

- backend deve continuar validando todas as permissoes
- app deve tratar `403` com mensagem clara

### Convite compartilhado fora de controle

Risco:

- convite encaminhado para pessoa errada.

Mitigacao:

- convite por e-mail continua sendo o controle da `v0.1`
- links compartilhaveis devem exigir regras adicionais antes de entrar no produto

### Contratos mudarem sem registro

Risco:

- app iOS quebrar por mudancas silenciosas na API.

Mitigacao:

- atualizar este documento quando contratos mudarem
- manter Swagger como referencia tecnica da API
