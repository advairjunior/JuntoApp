## Escopo tecnico da v0.3

A versao `0.3` deve implementar memorias privadas por encontro:

- marcar encontro como realizado
- listar encontros passados ou realizados do usuario
- criar memoria com foto
- listar memorias do encontro
- visualizar dados da memoria
- remover memoria propria
- preparar a tela mobile de midias para dados reais

Fotos sao P0.

Videos ficam fora da primeira implementacao tecnica da v0.3, salvo decisao posterior, porque aumentam risco de armazenamento, exibicao, tamanho de arquivo e performance.

## Estado atual da base

A base atual ja possui:

- `Encontro` como agregado principal do produto
- participantes por encontro
- presencas
- publicacoes no encontro
- imagem de capa do encontro
- foto de perfil do usuario
- tela mobile de midias com estado vazio
- armazenamento local em desenvolvimento para imagens em `wwwroot/arquivos`

A v0.3 deve aproveitar essa base sem voltar a centralizar o produto em grupos.

## Decisoes tecnicas da versao

### Midias como publicacoes do encontro

Fotos compartilhadas por participantes devem entrar no mesmo fluxo de publicacoes do encontro.

A entidade `MemoriaDoEncontro` continua existindo para preservar o conceito de memoria e compatibilidade dos endpoints atuais, mas a experiencia principal do app deve tratar uma midia como uma publicacao do mural do encontro. Assim, uma foto enviada aparece imediatamente na conversa/feed privado, e a tela de midias apenas filtra as publicacoes que possuem midia.

Motivo:

- evita dois lugares diferentes para o usuario procurar a mesma foto
- deixa conversa, organizacao e lembrancas no mesmo contexto
- aproxima a experiencia do comportamento esperado em grupos privados
- mantem a galeria como indice visual, nao como fluxo paralelo

### Fotos antes de videos

A primeira implementacao deve aceitar apenas imagens.

Tipos permitidos inicialmente:

- `image/jpeg`
- `image/png`
- `image/webp`

Motivo:

- reduz complexidade
- entrega valor rapido
- evita problemas de player, tamanho e streaming
- permite validar o album privado do encontro

### Armazenamento local privado por interface

Durante o desenvolvimento, as fotos de memorias serao salvas em:

```text
dados-privados/memorias
```

A camada `Aplicacao` deve depender de uma interface:

```text
IArmazenamentoDeMidiasDeMemoria
```

A camada `Infraestrutura` deve implementar:

```text
ArmazenamentoLocalDeMidiasDeMemoria
```

O caminho fisico deve ficar fora de `wwwroot`. A leitura ocorre exclusivamente pelas rotas autenticadas definidas na `DT-010`.

### URLs de midia

Na implementacao local, a API retorna a URL relativa de uma rota protegida para o arquivo.

O aplicativo mobile deve normalizar a URL para absoluta, como ja faz em imagens de perfil e capa.
O Flutter deve obter os bytes com JWT e renderizar a imagem em memoria, sem depender de uma URL estatica publica.

## Modelagem de dominio

### SituacaoDoEncontro

Adicionar o valor:

- `Realizado`

Regras:

- encontro planejado pode ser marcado como realizado
- encontro cancelado nao pode ser marcado como realizado
- encontro realizado nao pode ser cancelado por fluxo comum
- encontro realizado nao deve aceitar edicao comum de dados principais nesta primeira versao
- encontros podem receber memorias antes, durante e depois de acontecerem
- encontro realizado nao deve aparecer como proximo encontro

### MemoriaDoEncontro

Nova entidade no dominio `Encontros`.

Campos esperados:

- `Identificador`
- `IdentificadorDoEncontro`
- `IdentificadorDoUsuarioQuePublicou`
- `Legenda`
- `CriadoEm`
- `RemovidaEm`

Regras:

- memoria deve pertencer a um encontro
- memoria deve possuir autor
- legenda e opcional
- legenda deve ter tamanho maximo inicial de 280 caracteres
- memoria criada nao deve iniciar removida
- memoria removida deve preservar registro minimo para auditoria simples

### MidiaDaMemoria

Nova entidade no dominio `Encontros`.

Campos esperados:

- `Identificador`
- `IdentificadorDaMemoria`
- `Url`
- `NomeOriginal`
- `TipoDeConteudo`
- `TamanhoEmBytes`
- `CriadoEm`

Regras:

- midia deve pertencer a uma memoria
- URL deve ser obrigatoria
- nome original deve ser opcional ou sanitizado antes de persistir
- tipo de conteudo deve ser obrigatorio
- tamanho deve ser maior que zero
- tamanho maximo inicial recomendado: 10 MB

## Persistencia

### Tabelas novas

Tabelas esperadas:

- `midias_da_memoria`

### Relacionamentos

Relacionamentos esperados:

- `encontros` 1:N `memorias_do_encontro`
- `usuarios` 1:N `memorias_do_encontro`
- `memorias_do_encontro` 1:N `midias_da_memoria`

Indices esperados:

- `memorias_do_encontro.identificador_do_usuario_que_publicou`
- `midias_da_memoria.identificador_da_memoria`

A v0.3 deve criar uma migration nova.

A migration nao deve apagar nem recriar tabelas da v0.1 ou v0.2.

Deve adicionar o valor `Realizado` conforme o mapeamento atual de enum permitir.

### Repositorios

Preferir manter a simplicidade inicialmente:

- `IRepositorioDeMemoriasDoEncontro`

Operacoes esperadas:

- adicionar memoria
- adicionar midia da memoria
- listar memorias do encontro
- obter memoria por identificador
- atualizar memoria

### Armazenamento

Interface esperada:

```text

```

Responsabilidades:

- salvar arquivo

O armazenamento nao deve conter regra de permissao. Permissao fica nos casos de uso.

## Casos de uso

### MarqueEncontroComoRealizado

Objetivo:

- marcar encontro planejado como realizado.

Validacoes:

- usuario autenticado deve ser participante do encontro
- usuario deve ser organizador ou criador autorizado
- encontro deve existir para o usuario
- encontro deve estar planejado
- encontro cancelado deve ser bloqueado

### ListeEncontrosRealizadosDoUsuario

Objetivo:

- listar encontros realizados do usuario autenticado.

Validacoes:

- usuario autenticado deve ser participante
- retornar apenas encontros realizados
- ordenar por data de inicio decrescente

### CrieMemoriaDoEncontro

Objetivo:

- criar memoria com foto dentro de um encontro.

Validacoes:

- usuario autenticado deve ser participante do encontro
- encontro deve existir e estar acessivel ao participante
- arquivo deve ser imagem permitida
- arquivo deve respeitar tamanho maximo
- legenda deve respeitar tamanho maximo
- memoria deve ser associada ao encontro correto

### ListeMemoriasDoEncontro

Objetivo:

- listar memorias visiveis de um encontro para compatibilidade tecnica.

Na experiencia mobile, a galeria de midias deve preferir listar publicacoes do encontro com midia, porque essa e a fonte visual principal do mural.

Validacoes:

- usuario autenticado deve ser participante do encontro
- memorias removidas nao devem aparecer na listagem comum
- resultado deve ordenar por criacao ascendente ou descendente conforme UX definida no mobile

### RemovaMemoriaDoEncontro

Objetivo:

- remover memoria propria do encontro.

Validacoes:

- usuario autenticado deve ser participante do encontro
- usuario deve ser autor da memoria ou organizador, se moderacao for autorizada
- memoria deve pertencer ao encontro informado
- remocao deve ser idempotente quando possivel

## Contratos de aplicacao

Contratos esperados:

- `MarqueEncontroComoRealizadoComando`
- `CrieMemoriaDoEncontroComando`
- `RemovaMemoriaDoEncontroComando`
- `MemoriaDoEncontroResposta`
- `MidiaDaMemoriaResposta`

Os contratos devem usar portugues e expor apenas dados necessarios ao mobile.

## Contratos de API

### Marcar encontro como realizado

Rota:

```text
POST /api/encontros/{identificadorDoEncontro}/realizar
```

Resposta:

```text
204 No Content
```

### Listar encontros realizados do usuario

Rota:

```text
GET /api/encontros/realizados
```

Resposta:

```json
[
  {
    "identificador": "guid",
    "titulo": "Resenha do ADVA",
    "local": "Casa do ADVA",
    "urlDaImagemDeCapa": "/arquivos/encontros/imagem.jpg",
    "inicioEm": "2026-08-20T22:20:00Z",
    "situacao": "Realizado",
    "quantidadeDeMemorias": 8
  }
]
```

### Criar memoria

Rota:

```text
POST /api/encontros/{identificadorDoEncontro}/memorias
```

Formato:

```text
multipart/form-data
```

Campos:

- `arquivo`
- `legenda`

Resposta:

```json
{
  "identificador": "guid",
  "identificadorDoEncontro": "guid",
  "autor": "Deborah",
  "urlDaFotoDoAutor": "/arquivos/perfis/foto.jpg",
  "legenda": "Mesa pronta para a resenha",
  "criadoEm": "2026-08-20T23:10:00Z",
  "midias": [
    {
      "identificador": "guid",
      "url": "/arquivos/memorias/foto.jpg",
      "tipoDeConteudo": "image/jpeg",
      "tamanhoEmBytes": 580000
    }
  ]
}
```

### Listar memorias do encontro

Rota:

```text
GET /api/encontros/{identificadorDoEncontro}/memorias
```

### Remover memoria

Rota:

```text
DELETE /api/encontros/{identificadorDoEncontro}/memorias/{identificadorDaMemoria}
```

Resposta:

```text
204 No Content
```

## Regras de autorizacao

Todo endpoint de memoria deve:

- exigir JWT
- validar usuario autenticado
- validar participante ativo do encontro
- validar que a memoria pertence ao encontro informado
- retornar acesso negado generico quando o usuario nao tiver acesso

Recursos privados inacessiveis devem seguir `DT-004`.

## Riscos tecnicos

### Rotas privadas dependerem de autorizacao consistente

Risco:

- uma rota de arquivo pode expor conteudo caso deixe de validar a participacao ativa no encontro.

Mitigacao:

- manter arquivos fora de `wwwroot`, centralizar a leitura em caso de uso autenticado e cobrir acesso externo com testes de integracao.

### Upload pesar no mobile

Risco:

- fotos muito grandes prejudicarem desempenho.

Mitigacao:

- limitar tamanho no backend e avaliar compressao no mobile em etapa futura.

### Repositorio de encontros crescer demais

Risco:

- `IRepositorioDeEncontros` concentrar responsabilidades em excesso.

Mitigacao:

- começar simples e separar `IRepositorioDeMemoriasDoEncontro` se a legibilidade cair.
