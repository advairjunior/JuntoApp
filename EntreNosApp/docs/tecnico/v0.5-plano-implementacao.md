## Escopo tecnico da v0.5

A versao `0.5` deve implementar uma linha do tempo privada dos encontros do usuario:

- listar encontros passados ou realizados acessiveis ao usuario
- ordenar encontros de forma cronologica decrescente
- exibir resumo visual e textual do encontro
- destacar quantidade de memorias
- exibir imagem de capa ou fallback visual
- permitir filtros simples
- navegar para o detalhe do encontro existente
- navegar para as memorias do encontro existente

O nucleo P0 e a listagem privada.

Filtros simples entram como P1, desde que a listagem principal esteja estavel e clara.

## Decisoes tecnicas da versao

### Linha do tempo como consulta de leitura

A linha do tempo deve ser implementada inicialmente como uma consulta de leitura, nao como nova entidade persistida.

Motivo:

- a linha do tempo deriva de encontros, participantes, memorias e midias ja existentes
- evita duplicacao de dados
- reduz risco de inconsistencia
- preserva simplicidade da v0.5

### Nenhuma nova tabela inicialmente

A v0.5 nao deve criar tabela propria de linha do tempo.

Motivo:

- nao ha regra de negocio nova que exija persistencia propria
- os dados exibidos ja existem no banco
- uma tabela materializada seria overengineering neste momento

Se no futuro houver volume alto, caching, destaques manuais ou retrospectiva anual, uma tabela auxiliar ou materializacao podera ser reavaliada.

### Consulta especializada na infraestrutura

A aplicacao deve expor uma interface de leitura propria:

```text
IConsultaDeLinhaDoTempo
```

Motivo:

- a linha do tempo precisa agregar dados de varias tabelas
- um repositorio de dominio nao e o melhor lugar para uma consulta projetada para tela
- preserva o dominio sem dependencias de visualizacao
- permite otimizar a consulta no EF Core sem contaminar casos de uso

### Sem regra nova no dominio

A v0.5 nao deve adicionar entidade de dominio `LinhaDoTempo`.

Motivo:

- a linha do tempo e uma projecao de leitura
- as regras centrais continuam em `Encontro`, participantes e memorias
- evita criar um conceito de dominio artificial

### Filtros por enum seguro

Os filtros devem usar um enum simples na aplicacao:

```text
FiltroDaLinhaDoTempo
```

Valores iniciais:

- `Todos`
- `EsteMes`
- `UltimosTresMeses`
- `EsteAno`
- `Realizados`
- `ComMemorias`

Motivo:

- evita strings soltas nos casos de uso
- torna testes mais claros
- permite mapear query string da API de forma controlada

## Contratos de aplicacao

### ItemDaLinhaDoTempoResposta

Contrato esperado:

```text
ItemDaLinhaDoTempoResposta
```

Campos:

- `IdentificadorDoEncontro`
- `Titulo`
- `Descricao`
- `Local`
- `Inicio`
- `Situacao`
- `UrlDaImagem`
- `QuantidadeDeParticipantes`
- `QuantidadeDeMemorias`
- `QuantidadeDePublicacoes`
- `NomesDosParticipantesEmDestaque`

Observacoes:

- `UrlDaImagem` deve usar imagem de capa do encontro quando existir.
- Se nao houver capa, pode usar uma midia visual de memoria.
- Se nao houver imagem, deve retornar `null` e o mobile usa fallback visual.
- `NomesDosParticipantesEmDestaque` deve retornar poucos nomes, por exemplo ate 3, para evitar payload grande.

### LinhaDoTempoResposta

Contrato esperado:

```text
LinhaDoTempoResposta
```

Campos:

- `Filtro`
- `Itens`

Motivo:

- permite que a API retorne a lista e confirme o filtro aplicado
- facilita estados no mobile

### ListeLinhaDoTempoComando

Contrato esperado:

```text
ListeLinhaDoTempoComando
```

Campos:

- `IdentificadorDoUsuario`
- `Filtro`

## Caso de uso

### ListeLinhaDoTempo

Objetivo:

- listar encontros acessiveis ao usuario em formato de linha do tempo.

Validacoes:

- usuario deve estar autenticado
- filtro deve ser valido
- resultado deve conter apenas encontros dos quais o usuario participa

Fluxo:

1. validar identificador do usuario
2. normalizar filtro
3. consultar itens por `IConsultaDeLinhaDoTempo`
4. retornar `LinhaDoTempoResposta`

Regras:

- usuario sem encontros deve receber lista vazia
- lista deve ser ordenada por `Inicio` decrescente
- apenas encontros acessiveis devem aparecer
- encontros cancelados podem aparecer apenas se houver decisao explicita no plano de implementacao

Decisao inicial:

- exibir encontros realizados e encontros com data passada.
- nao exibir encontros cancelados na primeira entrega da v0.5.

Motivo:

- encontros realizados sao o centro natural da memoria
- encontros passados ainda planejados ajudam a encontrar momentos que talvez precisem ser marcados como realizados
- encontros cancelados podem poluir a historia sem entregar valor emocional inicial

## Persistencia e consultas

### Fonte dos dados

A consulta deve usar:

- `encontros`
- `participantes_do_encontro`
- `memorias_do_encontro`
- `midias_da_memoria`
- `publicacoes_do_encontro`

### Regra de acesso

A consulta deve filtrar por participante do encontro:

```text
participante.identificador_do_usuario == usuario atual
participante pode acessar encontro
```

O criterio tecnico exato deve reutilizar a mesma regra conceitual usada nos casos de uso de encontro:

- participante ativo
- convite aceito ou situacao que permita acesso
- usuario nao removido

### Ordenacao

Ordenacao inicial:

1. `Inicio` desc
2. `CriadoEm` desc, se necessario para desempate

### Imagem do item

Prioridade:

1. imagem de capa do encontro
2. primeira midia visual de memoria do encontro
3. `null`

O mobile deve cuidar do fallback visual quando `UrlDaImagem` for `null`.

### Quantidades

Quantidades esperadas:

- participantes acessiveis no encontro
- memorias do encontro
- publicacoes do encontro

As contagens devem ser feitas na consulta sem carregar colecoes completas em memoria.

### Paginacao

A primeira entrega pode retornar uma quantidade limitada fixa.

Decisao inicial:

- retornar ate 50 itens.

Motivo:

- evita payload grande
- simplifica a primeira experiencia
- ainda atende uso inicial

Paginacao com cursor fica fora da v0.5, salvo se os testes mostrarem necessidade imediata.

## API

### Endpoint principal

Rota:

```text
GET /api/linha-do-tempo
```

Query string:

```text
?filtro=todos
```

Valores aceitos:

- `todos`
- `este-mes`
- `ultimos-tres-meses`
- `este-ano`
- `realizados`
- `com-memorias`

Resposta:

```json
{
  "filtro": "Todos",
  "itens": [
    {
      "identificadorDoEncontro": "guid",
      "titulo": "Resenha do ADVA",
      "descricao": "Noite de resenha",
      "local": "Casa do ADVA",
      "inicio": "2026-08-20T22:00:00Z",
      "situacao": "Realizado",
      "urlDaImagem": "/arquivos/encontros/imagem.jpg",
      "quantidadeDeParticipantes": 8,
      "quantidadeDeMemorias": 14,
      "quantidadeDePublicacoes": 27,
      "nomesDosParticipantesEmDestaque": ["Deborah", "Advair", "Fabio"]
    }
  ]
}
```

Status esperados:

- `200 OK`
- `401 Unauthorized`

Nao deve existir rota para consultar linha do tempo de outro usuario na v0.5.

Motivo:

- reduz risco de privacidade
- preserva identidade privada
- evita linha do tempo publica

## Mobile

### Modelos

Modelos esperados:

- `LinhaDoTempoResposta`
- `ItemDaLinhaDoTempoResposta`
- `FiltroDaLinhaDoTempoItem`
- `ItemDaLinhaDoTempoItem`

### Servico da API

Adicionar ao cliente mobile:

```text
ListeLinhaDoTempoAsync
```

Parametros:

- token de acesso
- filtro
- cancellation token

### Tela

Tela esperada:

```text
TelaDeLinhaDoTempo
```

Modelo de visao esperado:

```text
TelaDeLinhaDoTempoModeloDeVisao
```

### Navegacao

A aba `Memorias` deve abrir a linha do tempo.

Motivo:

- o usuario ja entende `Memorias` como area para rever o que aconteceu
- evita criar nova aba
- preserva simplicidade da navegacao inferior

Ao tocar em um item:

- abrir detalhe do encontro existente

Acao secundaria:

- abrir midias do encontro quando houver memorias

Se a tela de detalhe ja der acesso claro as midias, a acao secundaria pode ser omitida na primeira entrega.

### Design mobile

A tela deve seguir o tema escuro atual do Junto.

Diretrizes:

- lista vertical simples
- cards com imagem quando houver
- fallback visual elegante quando nao houver imagem
- agrupamento visual por mes apenas se nao aumentar complexidade
- chips de filtro no topo
- texto curto e legivel
- estado vazio emocional, mas direto
- sem linguagem de rede social
- sem contadores de engajamento

### Estados da tela

Estados obrigatorios:

- carregando
- vazio sem encontros
- vazio por filtro
- erro
- lista com itens

## Riscos tecnicos

### Consulta pesada

Risco:

- agregar memorias, midias, publicacoes e participantes gerar consulta pesada.

Mitigacao:

- limitar a 50 itens
- projetar apenas campos necessarios
- usar contagens no banco
- evitar carregar colecoes completas
- revisar indices se necessario

### Vazamento de dados privados

Risco:

- retornar encontro ou memoria de usuario que nao participa.

Mitigacao:

- filtrar sempre por participante do encontro
- criar teste de integracao com usuario externo
- nao criar endpoint por identificador de outro usuario

### Duplicacao de experiencia

Risco:

- a linha do tempo tentar repetir detalhe, feed e midias.

Mitigacao:

- manter a tela como porta de entrada
- navegar para telas existentes
- limitar dados exibidos no item
