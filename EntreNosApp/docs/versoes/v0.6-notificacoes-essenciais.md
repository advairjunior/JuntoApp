# Projeto Encontros - Versao 0.6 - Notificacoes Essenciais

## Objetivo da versao

Adicionar notificacoes essenciais para ajudar o usuario a lembrar de encontros, convites e responsabilidades importantes.

A `v0.6` existe para reduzir esquecimentos e melhorar a organizacao dos encontros, mantendo a experiencia simples, privada e respeitosa.

## Valor para o usuario

Ao final da versao `0.6`, um usuario deve conseguir:

- ver avisos importantes dentro do aplicativo
- identificar convites pendentes
- lembrar de encontros proximos
- perceber alteracoes relevantes em encontros dos quais participa
- controlar configuracoes basicas de notificacao
- evitar excesso de interrupcoes

O valor principal desta versao e fortalecer organizacao e encontros sem criar notificacoes artificiais de engajamento.

## Escopo da versao

### Funcionalidades P0

- notificacao interna de convite para encontro
- notificacao interna de novo compromisso por convite para encontro
- notificacao interna de alteracao relevante no encontro
- indicador visual de notificacoes nao lidas
- tela ou area simples de notificacoes

### Funcionalidades P1

- configuracoes simples de notificacao
- lembrete de item sob responsabilidade do usuario
- marcacao de notificacao como lida
- limpeza visual de notificacoes antigas

### Funcionalidades P2

- lembrete automatico antes do encontro
- preparo tecnico para push notification futura
- registro de dispositivo do usuario
- preferencias por tipo de notificacao

## Fora do escopo

As funcionalidades abaixo nao devem ser implementadas na versao `0.6`:

- notificacoes publicitarias
- notificacoes de engajamento artificial
- notificacoes por curtidas, ranking ou popularidade
- campanhas promocionais
- push notification completa em producao
- integracao definitiva com APNs ou FCM
- automacoes complexas de agenda
- notificacoes para usuarios que nao participam do encontro
- notificacoes fora do contexto de convite, encontro, presenca ou combinado

Push notification real para iOS deve ser tratada como etapa futura ou subversao propria, porque envolve permissao do dispositivo, identificador de aparelho, provedor externo, certificados e validacao em ambiente Apple.

## Entidades conceituais

### NotificacaoDoUsuario

Representa um aviso privado criado para um usuario especifico.

Campos conceituais iniciais:

- identificador
- identificadorDoUsuario
- tipo
- titulo
- mensagem
- identificadorDoEncontro opcional
- identificadorDoConvite opcional
- identificadorDoItem opcional
- situacao
- criadaEm
- lidaEm opcional

Regras:

- notificacao sempre pertence a um usuario
- notificacao nao deve ser publica
- notificacao nao deve expor dados de encontro inacessivel
- notificacao deve apontar para uma acao util quando possivel
- notificacao deve usar linguagem clara e moderada

### PreferenciaDeNotificacao

Representa configuracoes simples do usuario.

Campos conceituais iniciais:

- identificadorDoUsuario
- notificacoesDeConviteAtivas
- lembretesDeEncontroAtivos
- notificacoesDeAlteracaoAtivas
- notificacoesDeCombinadosAtivas

Regras:

- preferencias pertencem ao usuario autenticado
- preferencias nao afetam outros participantes
- ausencia de preferencia deve usar padrao simples e seguro
- configuracoes nao devem criar tela complexa

## Tipos de notificacao

### Convite recebido

Objetivo:

- avisar que o usuario foi convidado para um encontro.

Valor:

- reduz chance de convite passar despercebido.

Acao esperada:

- abrir o encontro ou o fluxo de convite.

### Novo encontro

Objetivo:

- avisar participante convidado que existe um novo encontro.

Valor:

- ajuda o usuario a reconhecer rapidamente um compromisso novo.

Acao esperada:

- abrir detalhes do encontro.

### Lembrete de encontro

Objetivo:

- lembrar o usuario de um encontro proximo.

Valor:

- reduz esquecimentos e melhora presenca.

Acao esperada:

- abrir detalhes do encontro.

Status na v0.6:

- o tipo e a preferencia ficam preparados.
- a geracao automatica do lembrete depende de processamento agendado e foi movida para uma subversao futura.
- a v0.6 nao deve ser bloqueada por APNs, FCM ou agendador definitivo.

### Alteracao relevante

Objetivo:

- avisar sobre mudanca de data, horario, local ou cancelamento.

Valor:

- evita desencontro e confusao.

Acao esperada:

- abrir detalhes atualizados do encontro.

### Item sob responsabilidade

Objetivo:

- lembrar usuario de algo que combinou levar ou resolver.

Valor:

- reduz esquecimentos antes do encontro.

Acao esperada:

- abrir area de combinados do encontro.

## Regras de negocio especificas da versao

### Privacidade

- usuario deve visualizar apenas notificacoes criadas para ele.
- notificacao de encontro deve existir apenas para participante autorizado.
- se o usuario perder acesso ao encontro, a notificacao nao deve permitir abrir dados privados.
- endpoint de notificacoes deve exigir autenticacao.
- nao deve existir rota para listar notificacoes de outro usuario.

### Criacao de notificacoes

- convite aceito, cancelado ou invalido nao deve gerar acao valida.
- encontro cancelado nao deve gerar lembrete futuro.
- alteracoes irrelevantes nao devem criar notificacao.
- alteracoes repetidas devem evitar excesso de notificacoes.
- notificacao deve ser criada por evento de dominio ou caso de uso da aplicacao, nao diretamente pela tela.

### Leitura e limpeza

- usuario deve conseguir marcar notificacao como lida.
- notificacoes lidas podem continuar no historico curto.
- o app deve mostrar quantidade de nao lidas de forma discreta.
- nao deve haver gamificacao de notificacoes.

### Configuracoes

- preferencias devem ser simples.
- usuario deve poder desligar lembretes nao essenciais.
- configuracoes devem ser respeitadas nas novas notificacoes.
- notificacoes criticas de seguranca ou acesso podem receber regra especifica futura.

## Telas mobile previstas

### Area de notificacoes

Objetivo:

- concentrar avisos importantes do usuario.

Conteudo esperado:

- lista curta de notificacoes
- titulo da notificacao
- mensagem simples
- data relativa ou data curta
- indicador de nao lida
- acao ao tocar
- estado vazio
- estado de erro

### Indicador na tela inicial

Objetivo:

- mostrar discretamente que ha algo importante.

Conteudo esperado:

- icone de notificacao no topo
- marcador pequeno de nao lidas
- sem contadores chamativos
- sem animacoes excessivas

### Preferencias de notificacao

Objetivo:

- permitir controle basico de interrupcoes.

Conteudo esperado:

- toggles simples
- texto curto
- foco em convites, encontros, alteracoes e combinados
- sem configuracoes avancadas na primeira versao

## Decisoes de produto da versao

### Notificacao deve servir ao encontro, nao ao engajamento

Motivo:

- preserva a identidade do produto
- evita comportamento de rede social
- respeita a atencao do usuario
- reforca organizacao real

### Notificacao interna antes de push real

Motivo:

- valida regras e UX sem depender de infraestrutura externa
- reduz risco tecnico
- prepara o backend para push futura
- permite testar valor antes de lidar com APNs, certificados e permissao do iOS

### Poucos tipos de notificacao

Motivo:

- mantem simplicidade
- evita sobrecarga
- facilita QA
- reduz chance de spam interno

## Criterios de aceite da versao

A versao `0.6` sera considerada concluida quando:

- usuario autenticado conseguir listar suas notificacoes.
- usuario sem notificacoes visualizar estado vazio adequado.
- convite para encontro gerar notificacao para convidado.
- encontro novo gerar notificacao para participantes convidados, quando aplicavel.
- alteracao relevante de encontro gerar notificacao para participantes.
- encontro cancelado nao gerar lembrete futuro.
- usuario conseguir marcar notificacao como lida.
- indicador de nao lidas aparecer no app de forma discreta.
- preferencias simples forem exibidas e salvas.
- usuario externo nao conseguir acessar notificacoes de outro usuario.
- testes automatizados cobrirem privacidade e regras principais.
- app compilar sem erros.

## Riscos da versao

### Excesso de notificacoes

Risco:

- usuario sentir que o app incomoda.

Mitigacao:

- limitar tipos iniciais
- criar notificacoes apenas para eventos importantes
- oferecer preferencias simples

### Complexidade tecnica prematura

Risco:

- tentar implementar push completa antes de validar regras internas.

Mitigacao:

- iniciar por notificacoes internas
- isolar interfaces para envio futuro
- documentar push como etapa posterior

### Vazamento de privacidade

Risco:

- notificacao revelar encontro privado para usuario sem acesso.

Mitigacao:

- notificacao pertence sempre ao usuario
- validar acesso ao abrir destino
- testar cenarios de usuario externo

## Ordem recomendada de implementacao futura

Quando a implementacao for autorizada, a ordem recomendada sera:

1. Criar plano tecnico da `v0.6`.
2. Modelar notificacao e preferencias.
3. Criar contratos de aplicacao.
4. Criar casos de uso de listagem, leitura e preferencias.
5. Gerar notificacoes nos fluxos de convite e alteracao de encontro.
6. Expor endpoints privados.
7. Criar testes automatizados.
8. Criar area mobile de notificacoes.
9. Adicionar indicador discreto na tela inicial.
10. Criar tela simples de preferencias.
11. Executar QA da versao.
