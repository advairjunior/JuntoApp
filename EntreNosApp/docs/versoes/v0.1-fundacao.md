# Projeto Encontros - Versao 0.1 - Fundacao

## Objetivo do documento

Este documento detalha o plano de execucao da versao `0.1 - Fundacao` do Projeto Encontros.

Ele transforma o roadmap e o backlog inicial em um escopo executavel para a primeira entrega do produto.

Este documento nao substitui os documentos de produto. Ele deve ser lido em conjunto com:

- `../produto/00-visao-produto.md`
- `../produto/01-roadmap-versoes.md`
- `../produto/02-arquitetura-inicial.md`
- `../produto/03-regras-de-produto.md`
- `../produto/04-backlog-inicial.md`

## Objetivo da versao

Criar a base minima para que o Projeto Encontros exista como produto privado para grupos.

A primeira implementacao da versao `0.1` e uma entrega tecnica backend-only.

Ela deve permitir, via API, que um usuario crie conta, autentique-se, crie um grupo privado, convide pessoas, aceite convites, visualize seus grupos e tenha controle basico dos membros.

Esta versao nao precisa entregar ainda a organizacao de encontros. Ela prepara o terreno para que a versao `0.2` possa implementar encontros com seguranca e coerencia.

## Valor para o usuario

Ao final da fundacao backend da versao `0.1`, a API deve permitir:

- criar sua conta
- autenticar uma sessao
- criar um grupo privado
- convidar pessoas para o grupo
- entrar em um grupo por convite
- visualizar os grupos dos quais participa
- abrir um grupo e reconhecer aquele espaco como o ponto central da convivencia

O valor principal desta versao e estabelecer confianca, privacidade e a estrutura basica de grupos.

## Escopo da versao

### Funcionalidades P0

- `BE-001 - Cadastro de usuario`
- `BE-002 - Login de usuario`
- `BE-003 - Renovacao e revogacao de sessao`
- `BE-004 - Criacao de grupo`
- `BE-005 - Listagem dos grupos do usuario`
- `BE-006 - Visualizacao basica de grupo`

- `BE-008 - Aceite de convite`

- `BE-009 - Gerenciamento basico de membros`

## Fora do escopo

As funcionalidades abaixo nao devem ser implementadas na versao `0.1`:

- criacao de encontros
- confirmacao de presenca
- album de fotos ou videos
- memorias
- linha do tempo
- listas colaborativas
- notificacoes push
- setlists
- estatisticas
- comentarios
- chat
- feed publico
- perfis publicos
- funcionalidades de rede social

Qualquer tentativa de incluir esses recursos na `v0.1` deve ser recusada ou adiada para preservar foco e simplicidade.

## Entidades iniciais

### Usuario

Representa uma pessoa que usa o Projeto Encontros.

Campos conceituais iniciais:

- id
- nome
- email
- senha protegida
- data de criacao
- situacao

Regras:

- e-mail deve ser unico
- senha nunca deve ser armazenada em texto puro
- usuario pode participar de varios grupos
- usuario deve visualizar apenas grupos dos quais participa

### TokenDeAtualizacao

Representa uma sessao renovavel de usuario.

Campos conceituais iniciais:

- id
- identificadorDoUsuario
- token protegido ou identificador seguro
- data de expiracao
- data de revogacao
- data de criacao

Regras:

- token expirado nao deve renovar sessao
- token revogado nao deve renovar sessao
- logout deve revogar o token ativo

### Grupo

Representa um grupo privado.

Campos conceituais iniciais:

- id
- nome
- descricao opcional
- identificadorDoUsuarioDono
- data de criacao
- situacao

Regras:

- grupo deve ser privado por padrao
- grupo deve ter um dono
- grupo deve possuir nome claro
- grupo deve ter pelo menos um membro responsavel

### MembroDoGrupo

Representa a participacao de um usuario em um grupo.

Campos conceituais iniciais:

- id
- identificadorDoGrupo
- identificadorDoUsuario
- papel
- data de entrada
- situacao

Regras:

- usuario nao pode ser duplicado como membro do mesmo grupo
- apenas membros podem visualizar dados privados do grupo
- grupo deve manter pelo menos um responsavel

### ConviteDoGrupo

Representa um convite para entrada em grupo.

Campos conceituais iniciais:

- id
- identificadorDoGrupo
- emailConvidado ou identificador do convidado
- identificadorDoUsuarioQueConvidou
- situacao
- data de criacao
- data de expiracao opcional
- data de aceite opcional

Regras:

- convite deve pertencer a um grupo
- convite deve possuir estado
- convite aceito nao deve ser reutilizado de forma insegura
- convite nao deve expor dados sensiveis do grupo

Estados candidatos:

- pendente
- aceito
- recusado
- expirado
- cancelado

## Papeis iniciais

Para a versao `0.1`, a recomendacao e iniciar com dois papeis:

- dono do grupo
- membro do grupo

O papel de administrador deve permanecer adiado ate haver necessidade real.

### Dono do grupo

Pode:

- visualizar o grupo
- editar dados basicos do grupo, se essa tela existir na versao
- convidar membros
- visualizar membros
- remover membros comuns

Nao deve:

- remover a si mesmo deixando o grupo sem responsavel
- transformar o grupo em publico

### Membro do grupo

Pode:

- visualizar o grupo
- visualizar outros membros
- aceitar participacao no grupo

Nao deve:

- remover membros
- acessar grupos externos
- gerenciar convites, salvo se essa permissao for explicitamente revisada no futuro

## APIs necessarias

As rotas abaixo sao conceituais. A forma final deve ser validada na implementacao respeitando a arquitetura definida em `../produto/02-arquitetura-inicial.md`.

### Autenticacao

```text
POST /api/autenticacao/cadastro
POST /api/autenticacao/login
POST /api/autenticacao/renovar-sessao
POST /api/autenticacao/sair
```

### Usuario

```text
GET /api/usuarios/eu
```

### Grupos

```text
POST /api/grupos
GET /api/grupos
GET /api/grupos/{identificadorDoGrupo}
```

### Convites

```text
POST /api/grupos/{identificadorDoGrupo}/convites
GET /api/convites
GET /api/convites/{identificadorDoConvite}
POST /api/convites/{identificadorDoConvite}/aceitar
POST /api/convites/{identificadorDoConvite}/recusar
```

### Membros

```text
GET /api/grupos/{identificadorDoGrupo}/membros
DELETE /api/grupos/{identificadorDoGrupo}/membros/{identificadorDoMembro}
```

Objetivo:

## Regras de negocio especificas da versao

### Conta

- E-mail deve ser unico.
- Senha deve ser protegida.
- Usuario nao autenticado nao deve acessar dados privados.
- Usuario autenticado deve acessar apenas seus proprios recursos.

### Sessao

- Access token deve ter vida curta.
- Refresh token deve ser revogavel.
- Logout deve encerrar a sessao renovavel.
- Tokens invalidos nao devem permitir acesso.

### Grupo

- Grupo deve ser privado por padrao.
- Todo grupo deve ter um dono.
- Criador do grupo deve virar dono automaticamente.
- Apenas membros devem visualizar grupo.
- Grupo deve manter pelo menos um responsavel.

### Convite

- Apenas dono do grupo pode criar convite na `v0.1`.
- Convite deve iniciar como pendente.
- Usuario convidado deve conseguir listar seus convites pendentes.
- Convite aceito deve criar vinculo de membro.
- Convite aceito nao deve ser reutilizado.
- Convite invalido nao deve permitir entrada.

### Membros

- Usuario pode participar de mais de um grupo.
- Usuario nao pode aparecer duplicado no mesmo grupo.
- Membro removido nao deve acessar o grupo.
- Dono nao deve remover a si mesmo se isso deixar o grupo sem responsavel.

## Decisoes tecnicas da versao

### Backend

- Usar ASP.NET Core Web API.
- Seguir Clean Architecture.
- Manter regras de negocio fora dos controllers.
- Usar Entity Framework Core com PostgreSQL.
- Usar JWT com Refresh Token.
- Usar FluentValidation para validacoes de entrada.
- Usar Swagger para documentacao da API.

### Mobile

- Cliente iOS sera priorizado quando o mobile for iniciado.
- Usar .NET MAUI com foco inicial em iOS.
- Preservar Android como possibilidade futura sem bloquear o primeiro ciclo mobile.
- Seguir MVVM simples.
- Evitar duplicacao de telas.
- Reutilizar componentes.
- Priorizar fluxos simples e uso com uma mao.

### Banco de dados

Tabelas esperadas:

- usuarios
- tokens_de_atualizacao
- grupos
- membros_do_grupo
- convites_do_grupo

Indices esperados:

- e-mail unico em usuarios
- combinacao unica de identificadorDoGrupo e identificadorDoUsuario em membros_do_grupo
- indices para consultas por identificadorDoUsuario e identificadorDoGrupo

### Testes

Devem existir testes para:

- cadastro com e-mail duplicado
- login com credenciais invalidas
- renovacao de token invalido
- criacao de grupo por usuario autenticado
- bloqueio de criacao de grupo por usuario nao autenticado
- aceite de convite valido
- bloqueio de convite invalido
- impedimento de membro duplicado
- bloqueio de acesso a grupo externo

## Criterios de aceite da versao

A versao `0.1` sera considerada concluida quando:

- usuario conseguir criar conta
- usuario conseguir fazer login
- usuario conseguir renovar sessao
- usuario conseguir fazer logout
- usuario autenticado conseguir criar grupo
- criador virar dono do grupo
- usuario conseguir listar seus grupos
- usuario conseguir abrir grupo do qual participa
- dono conseguir criar convite
- usuario conseguir aceitar convite valido
- usuario virar membro apos aceitar convite
- dono conseguir visualizar membros
- dono conseguir remover membro comum
- usuario externo nao conseguir acessar grupo privado
- dados de grupos nao vazarem entre usuarios
- fluxos principais tiverem estados de erro e vazio
- documentacao da versao estiver atualizada

## Riscos da versao

### Escopo crescer cedo demais

Risco:

- tentar incluir encontros, memorias ou notificacoes antes da fundacao estar pronta.

Mitigacao:

- manter `v0.1` limitada a conta, autenticacao, grupos, convites e membros.

### Permissoes ficarem complexas cedo demais

Risco:

- criar muitos papeis e regras administrativas antes de validar necessidade.

Mitigacao:

- iniciar apenas com dono e membro.

### Privacidade falhar na base

Risco:

- usuarios acessarem grupos de outras pessoas por falha de autorizacao.

Mitigacao:

- validar pertencimento ao grupo em todos os casos de uso privados.

### Experiencia inicial parecer generica

Risco:

- a fundacao parecer apenas cadastro e login, sem identidade de produto.

Mitigacao:

- comunicar que o grupo e um espaco privado para convivencia, encontros futuros e memorias.

## Ordem recomendada de implementacao futura

Quando a implementacao for autorizada, a ordem recomendada sera:

1. Estrutura da solucao.
2. Configuracao base da API.
3. Configuracao base do banco.
4. Entidades da fundacao.
5. Autenticacao e sessao.
6. Grupos.
7. Convites.
8. Membros.
9. Testes automatizados.
10. Revisao de prontidao para cliente iOS.
11. Spike mobile para validar build, API, armazenamento seguro e navegacao.
12. Revisao dos resultados do spike mobile.
13. Aplicativo mobile com fluxos principais, em etapa propria.
14. Revisao de QA mobile, em etapa propria.
